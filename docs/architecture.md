# 技能学习与互换平台：产品与后端架构

## 产品结构

发现页以「我想学的」驱动课程推荐和筛选。用户档案分别保存可教授的技能与学习兴趣，不把二者混成单一标签。课程是独立实体：一个老师可以发布多个课程，同一种技能可以有不同课程设计与价格。

- **发现技能**：多列封面卡片、学习成果摘要、价格、学习方式和老师信息；兴趣优先，也保留探索新技能的入口。
- **课程详情**：Description、适合人群、课时安排、课程大纲、试讲方案与价格、教案、视频、成果作品、验收标准。
- **我的空间**：用户资料、能教/想学、我的发布、收藏、交换邀请。
- **订单中心**：学员的购买记录与老师的授课记录；每笔订单固定购买时的价格及课程约定。

当前推荐规则是可解释的标签匹配：符合学习兴趣优先，双方技能互补再次加权。不是机器学习模型，也不把规则分数宣称为成功概率。后续可在获得用户同意后引入浏览、收藏与购买信号；不让付费曝光伪装成自然推荐。

## 当前实现与生产边界

| 模块 | 当前可体验 | 生产系统需要 |
| --- | --- | --- |
| 用户 | 本机演示身份切换、档案 | 服务端认证、会话、身份校验、权限控制 |
| 内容 | 封面上传到浏览器、作品与媒体链接 | 对象存储、上传校验、转码、访问控制、内容管理 |
| 课程 | 创建、编辑、详情、筛选 | 数据库、版本管理、上下架与审核 |
| 订单 | 买方/卖方、课程快照、状态与历史 | 服务端金额校验、并发控制、幂等、不可变事件日志 |
| 付款 | 本机模拟付款/退款/结算 | 支付服务商、服务端回调验证、支付记录与对账 |
| 交付 | 文本交付、验收、要求补充 | 文件附件、沟通记录、争议处理和通知 |

GitHub Pages 继续托管前端。真实业务由单独的 HTTPS API、关系型数据库与对象存储承载。支付密钥、会话凭据和支付回调验证必须留在服务端，不能放在前端或 GitHub 仓库中。

演示版课程价格使用整数分，订单创建时保存快照，课程修改不能改变已购订单的价格与约定。真实课程下架同样不删除历史订单。

## 订单与支付流程

演示状态为：

```text
待付款 ──模拟付款──> 学习中 ──老师提交交付──> 待验收 ──学员确认──> 已完成
  └──取消──> 已取消       └──模拟退款──> 已退款       └──要求补充──> 学习中
```

生产系统应将业务订单状态与支付状态分开：

1. 用户提交课程 ID 和产品类型，服务端重新读取价格并锁定订单快照，不采信客户端金额。
2. 服务端创建支付单，向支付服务商获取收银台或支付参数；重复请求使用幂等键。
3. 只有通过验签、金额和币种核对的服务端回调才能将支付状态置为成功。浏览器跳转成功页不能证明付款。
4. 课程订单进入履约中。老师只能提交自己订单的交付；学员只能验收自己的购买。
5. 验收写入独立记录。真实结算采用支付服务商支持的商户结算方案；不能把前端「已完成」等同于款项已结算。
6. 退款先申请，再由服务端审核和调用支付渠道，渠道确认后才标记退款成功。回调需去重，并支持补偿、失败重试与对账。
7. 已交付的异议进入补充交付或争议处理；是否自动验收、退款时限、平台费用和老师结算周期须先确定产品规则。

演示中「未交付可直接全额模拟退款」只用于验证路径，不是正式退款承诺。免费试讲仍保留预约/确认记录，但真实系统不创建无意义的零元扣款。

## API 边界草案

- `GET/PATCH /me`、`GET/PUT /me/skills`
- `GET /courses`、`POST /courses`、`PATCH /courses/:id`、`GET /courses/:id`
- `POST /uploads`：服务端发放受限上传凭据，校验大小、类型与归属。
- `POST /orders`、`GET /orders?role=buyer|seller`、`GET /orders/:id`
- `POST /orders/:id/payment`、`POST /payments/webhook`
- `POST /orders/:id/deliveries`、`POST /orders/:id/acceptance`
- `POST /orders/:id/refund-requests`、`POST /orders/:id/revision-requests`

所有变更端点在服务端校验身份、资源归属和当前状态，并以数据库事务写入业务状态与事件。订单详情与课程资产不能仅凭可猜测 ID 访问。

## 下一阶段需要确认

实际收款前，需要确定部署后端、支付地区与币种、商户主体及支付渠道，并明确课程定价、退款、争议、结算政策。随后先接通支付沙箱与真实账号，再验证支付回调、幂等和对账，最后开放真实交易。
